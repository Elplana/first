1. PROJECT OVERVIEW
================================================================================

1.1 Project Identity & Classification
- Name: FootballIQ
- Nature: AI-powered European football player market valuation platform (SaaS).
- Delivery Medium: Web application featuring a modern React frontend and a
  high-performance FastAPI backend serving serialized machine learning pipelines.
- Core Identity: An editorial football market observatory combining broadsheet
  typographic precision with statistical modeling, avoiding generic dashboard
  and neon-heavy gaming aesthetics.

1.2 Problem Statement
European association football transfers represent a multi-billion euro global
market characterised by substantial information asymmetry, speculative pricing,
and subjective valuation biases. Club sporting directors, recruitment analysts,
scouts, journalists, and fans often rely on heuristic estimates or proprietary
portals whose methodologies lack transparent statistical modeling. Market values
are heavily skewed by club financial clout, league profile, and viral media
hype rather than underlying per-90 pitch output, underlying expected metrics
(xG, xA), and contextual athletic parameters.

1.3 Proposed Solution
FootballIQ provides a rigorous, data-driven player valuation observatory. By
aggregating granular match performance metrics across 3,670 European player
profiles spanning 8 major leagues, FootballIQ applies advanced gradient boosting
regression to infer fair market valuations (in Euros). The platform provides
transparent model inputs, per-90 feature normalizations, relative valuation
benchmarks, and instant multi-metric profiling without black-box opacity.

1.4 Target Audience & User Personas
- Football Analysts & Data Scouts: Assessing transfer targets against league-wide
  efficiency benchmarks and identifying undervalued assets.
- Club Sporting Directors & Recruitment Staff: Sanity-checking asking prices and
  salary-to-valuation ratios using statistically normalized performance inputs.
- Sports Journalists & Content Creators: Referencing objective market valuations
  and editorial performance snapshots for transfer deadline reports.
- Dedicated Supporters & Enthusiasts: Interactively testing hypothetical player
  performance curves, simulating valuation changes based on goal or assist tallies.

1.5 Primary Objectives & Expected Outcomes
- Deliver sub-100ms inference on player market values via a modular REST API.
- Provide a clean, distraction-free editorial frontend adhering to a strict
  achromatic visual design system (Graphite, Canvas White, Ash, Ember Orange).
- Normalize raw statistical totals into per-90 metrics to eliminate bias towards
  players who accumulated high volumes solely through playing time.
- Normalize valuation distributions via natural logarithmic transformations
  (log1p) to accurately model both lower-tier squad players and elite €150M+
  outliers without distortion.

2. IMPLEMENTATION AUDIT & FEATURE CLASSIFICATION
================================================================================

This audit strictly distinguishes between fully working features, partially
implemented elements, planned architecture, and unverified components based on
source-code inspection and runtime execution.

[A] Fully Implemented Features:
1. Backend REST API (FastAPI):
   - GET / (Service metadata and documentation pointers).
   - GET /health (Live model availability check and path resolution).
   - POST /api/v1/predict (Full Pydantic payload validation, automatic per-90
     feature calculation, log-space prediction, expm1 inverse transformation).
   - Global exception handling and JSON error formatting.
2. Dual-Engine Prediction Architecture:
   - Primary: Scikit-learn Pipeline (ColumnTransformer + GradientBoostingRegressor)
     loaded from `footballiq_best_model.joblib`.
   - Fallback: Pure NumPy Ridge regression solver (`_init_numpy_engine`) solving
     (X^T X + λI)^-1 X^T y from `cleaned_player_data.csv` on runtime failure.
3. Machine Learning Modeling & Artifacts:
   - 5-fold cross-validated comparison pipeline across 7 regressor families.
   - Serialized joblib artifact (`footballiq_best_model.joblib`).
   - Generation of EDA plots and model performance diagnostics in `eda_plots/`
     and `model_results/`.
4. Frontend Application Shell & Routing (React + Vite + React Router):
   - Multi-route client-side router (`/`, `/predict`, `/valuation`, `/result`,
     `/players`, `/methodology`).
   - Editorial sticky header (`Navbar.jsx`) with mobile drawer navigation and
     active orange underline accents.
   - Comprehensive footer (`Footer.jsx`) with dynamic year, platform status pill,
     and league coverage directories.
   - Global CSS tokens (`tokens.css`) enforcing spacing, typography, and palette.
5. Interactive Player Database (`Players.jsx`):
   - Full client-side dataset browsing across 3,670 player records.
   - Text search filter, league dropdown, position filter, column sorting
     (Name, League, Position, Market Value, Rating), and pagination (20 per page).
   - Row-level "Evaluate" action routing selected profile into the prediction engine.
6. Valuation Engine Form & Results (`PredictionForm.jsx`, `PredictionResult.jsx`):
   - Form pre-filling from selected database records or preset player chips
     (Bukayo Saka, Viktor Gyökeres, Martin Odegaard, Declan Rice, Eberechi Eze).
   - Comprehensive numerical inputs (playing time, attacking stats, xG, xA,
     defensive actions, discipline, rating).
   - Form validation displaying inline error notices.
   - Valuation result card featuring raw Euro valuation, formatted string,
     supporting metric cards, and horizontal comparative benchmark bars.
7. Scroll Reveal & Intersection Observer Animations:
   - `SectionReveal.jsx` and `useScrollReveal.js` driving progressive fade-and-rise
     scroll reveals using `cubic-bezier(0.22, 1, 0.36, 1)`.

[B] Partially Implemented Features:
1. Hero Section Scroll Depth Effect (`Hero.jsx`):
   - Multi-layer 3D stacking is implemented using 5 absolute CSS layers
     (stadium background, halo blur, typography, Jude Bellingham cutout, search bar).
   - Scroll-linked scale, opacity, blur, and translation are implemented via
     `requestAnimationFrame` and scroll listeners.
   - Discrepancy: Implemented piecewise keyframe values differ slightly from the
     original design document target milestones (documented in Section 5).
2. Standalone Result Route (`Result.jsx`):
   - The `/result` route is registered in `App.jsx`, but the primary flow in
     `Predict.jsx` conditionally renders `<PredictionResult />` directly in-place
     instead of pushing to `/result`. `/result` only renders if state is passed
     explicitly, showing an empty state otherwise.
3. Secondary Search Component (`SearchBar.jsx`):
   - An older `SearchBar.jsx` component exists in `src/components/`, while `Hero.jsx`
     utilizes the newer `PlayerSearch.jsx` component.

[C] Planned / Not Implemented Features:
1. Dynamic Player Image Roster / Individual Cutouts:
   - The dataset (`playersData.json`, `cleaned_player_data.csv`) contains NO image
     URLs or player photo references.
   - The local asset directories contain only Jude Bellingham hero imagery and one
     generic player portrait (`player_portrait.png`).
   - Selecting a player does NOT display that specific player's portrait on the
     result page or prediction form.
2. Production Database Storage (SQL / PostgreSQL / SQLite):
   - The project currently relies entirely on static CSV files and a bundled
     `playersData.json` file (3.36 MB). No external relational database or ORM
     is connected.
3. Authentication, User Accounts & Saved Valuations:
   - The UI includes "Sign in" and "Get started" CTA links, but no authentication
     backend, user session management, or valuation saving functionality exists.
4. Historical Valuation Tracking / Multi-Season Progression:
   - Visual charts show relative comparisons against static multipliers rather
     than true historical player valuation time-series curves.

[D] Broken / Unverified Features:
1. Standalone `PlayerPortrait.jsx` Component:
   - Implemented in `src/components/PlayerPortrait.jsx` with desktop parallax,
     warm halo, and micro-annotations, but is currently UNMOUNTED in all active
     pages (unused in `Home.jsx` and `Predict.jsx`).
2. Python 3.14 Joblib Unpickling Latency:
   - On Windows environments running Python 3.14, loading `footballiq_best_model.joblib`
     experiences an initial 15-20 second cold-start delay during module import
     due to OpenMP/threadpool initialization checks in scikit-learn.

4. DESIGN SYSTEM & EDITORIAL AESTHETIC SPECIFICATION
================================================================================

4.1 Visual Philosophy
FootballIQ rejects the visual cliches of consumer web apps: neon gradients,
glassmorphism, floating dashboard widgets, rounded candy buttons, and aggressive
micro-interactions. Instead, it embodies a quiet, high-authority "editorial data
observatory" modeled on prestige financial print journals and technical football
analytics publications.

Key Principles:
- Approximately 95% Achromatic: Visual rhythm is established through tonal warm
  grays, high-contrast typography, and generous whitespace.
- Restrained Color Punctuation: Ember Orange (#FF682C) is never used as a filled
  button background; it serves exclusively as a functional accent (live status
  dots, active tab underlines, small data highlights).
- Architectural Geometry: Sharp rectangular buttons (border-radius: 0px) create
  deliberate tension against subtly rounded data containers.
- Editorial Photography: Football players are presented in high-contrast,
  monochromatic, desaturated portraits rather than vibrant action collages.
- Unobstructed Subjects: Player portraits are never covered by floating stat
  cards, chart overlays, or large valuation callout boxes.

5. HERO SECTION: 3D DEPTH, LAYERING & SCROLL INTERACTION
================================================================================

5.1 Architectural Stacking & Z-Index Hierarchy
The Hero section (`src/components/Hero.jsx` and `src/components/Hero.css`) is
engineered as an editorial 3D composition with 5 distinct physical layers:

Layer 1 — Background Stadium Atmosphere (z-index: 1):
- Element: `.hero-background-layer` containing `hero-player.png`.
- Styling: Positioned absolute, object-fit cover, scaled to 1.04, opacity 0.55.
- Filters: `grayscale(100%) brightness(95%) contrast(98%) blur(6px)`.
- Framing: Top linear gradient fade (90px height) and bottom linear gradient
  fade (220px height) smoothly merging into Canvas White (#FFFFFF).

Layer 2 — Soft Atmospheric Fog / Halo (z-index: 2):
- Element: `.hero-halo-layer`.
- Styling: Centered radial gradient ellipse (70% × 50% at 50% 40%) with opacity
  shifting from rgba(255,255,255,0.85) to transparent, combined with a 1px blur.
- Function: Creates an ethereal glow behind the subject, separating foreground
  from the stadium stands.

Layer 3 — Typography Layer (z-index: 3):
- Element: `.hero-typography-layer`.
- Contents:
  1. Eyebrow label: "AI-POWERED PLAYER VALUATION" + 6px Ember Orange pulsing dot.
  2. Display Headline: "Know what a player is worth." (66px, weight 400).
- Text shadow: `0 1px 12px rgba(255, 255, 255, 0.8)` ensuring total legibility
  against background contours.

Layer 4 — Isolated Player Cutout Layer (z-index: 4):
- Element: `.hero-player-layer` containing `hero-player-cutout.png` (Jude Bellingham).
- Cutout Dimensions: Height 660px, width auto, object-fit contain.
- Filters: `grayscale(100%) contrast(105%) drop-shadow(0 14px 28px rgba(0,0,0,0.16))`.
- Alignment: Sits directly in the center, emerging in front of the stadium but
  positioned so that facial features and upper torso remain completely
  unobstructed by typography or input boxes.

Layer 5 — Search UI Layer (z-index: 5):
- Element: `.hero-ui-layer` hosting `<PlayerSearch />`.
- Composition: Top-level interactive search input (height 60px) paired with a
  0px-radius "Get valuation →" Graphite button. Positioned below the headline,
  allowing seamless user entry without occluding the player portrait.

5.2 Scroll-Linked Depth Interaction: Specification vs Implementation
The intended design specification outlines a multi-stage recession where the
foreground player cutout appears to step backwards into the stadium mist as the
user initiates scrolling, while the headline and navigation remain crisp.

Target Specification Milestones:
- Scroll 0%:   Scale: 1.00 | Opacity: 1.00 | Blur: 0.0px | Position: Normal
- Scroll 25%:  Scale: 0.93 | Opacity: 0.96 | Blur: 0.5px | Slight depth recession
- Scroll 50%:  Scale: 0.82 | Opacity: 0.85 | Blur: 1.5px | Mid-plane transition
- Scroll 75%:  Scale: 0.68 | Opacity: 0.65 | Blur: 3.0px | Entering background
- Scroll 100%: Scale: 0.55 | Opacity: 0.35 | Blur: 6.0px | Merged into background

Actual Code Implementation in `src/components/Hero.jsx`:
The actual implementation uses a piece-wise linear interpolation running inside a
`requestAnimationFrame` loop tracking `window.scrollY` over a `maxScroll = 450px`
domain:

Progress Range  Scale Range     Opacity Range   Blur Range      TranslateY Range
--------------------------------------------------------------------------------
0.00 – 0.25     1.00 → 0.92     1.00 → 0.95     0.0px → 0.5px   0px → -12px
0.25 – 0.50     0.92 → 0.80     0.95 → 0.82     0.5px → 2.0px   -12px → -28px
0.50 – 0.75     0.80 → 0.68     0.82 → 0.60     2.0px → 4.0px   -28px → -44px
0.75 – 1.00     0.68 → 0.55     0.60 → 0.30     4.0px → 7.0px   -44px → -60px

Differences Noted:
1. At 50% scroll: Implemented opacity is 0.82 (spec: 0.85); blur is 2.0px (spec: 1.5px).
2. At 75% scroll: Implemented opacity is 0.60 (spec: 0.65); blur is 4.0px (spec: 3.0px).
3. At 100% scroll: Implemented opacity is 0.30 (spec: 0.35); blur is 7.0px (spec: 6.0px).
4. Vertical translation: The code adds an explicit vertical drift (-60px total)
   to ensure the player recedes upwards into the viewport fold smoothly.
5. Tested Status: Fully functional and verified in browser environments. Responds
   passively to scroll events with zero layout thrashing.

6. FRONTEND ARCHITECTURE (REACT + VITE)
================================================================================

6.1 Technology Stack & Tooling
- Core Library: React 18.3.1 (using functional components and hooks).
- Build Tool: Vite 5.4.21 (Fast ESM development and Rollup production bundling).
- Router: React Router DOM 6.26.2 (declarative client-side routing).

- Styling Architecture: Hybrid architecture pairing Tailwind CSS utility classes

6.2 Route Architecture (`src/App.jsx`)
The application defines 6 primary routes wrapped in `<ScrollToTop />`:
- `/`: `<Home />` — Editorial landing page featuring the 3D Hero, "How It Works"
  process breakdown, sample player cards, and methodology teaser.
- `/predict`: `<Predict />` — Interactive valuation engine containing the full
  input configuration form, loading indicators, and in-place valuation results.
- `/valuation`: `<Predict />` — Route alias redirecting to `<Predict />`, handling
  query string parameters (e.g. `/valuation?player=Jude%20Bellingham`).
- `/result`: `<Result />` — Standalone valuation report route displaying a
  dedicated summary view when routed with navigation state.
- `/players`: `<Players />` — Comprehensive 3,670-player database browser with
  search, multi-column sorting, league/position filters, and pagination.
- `/methodology`: `<Methodology />` — Deep technical documentation page detailing
  data sources, log transformation formulas, feature engineering, and metrics.

6.3 Component Breakdown
- `Navbar.jsx`: Desktop horizontal nav with active page indicator (Ember Orange
  hairline) and mobile hamburger drawer. Includes "Get started" CTA button.
- `Hero.jsx`: Multi-layered visual anchor executing the 3D player recession effect.
- `PlayerSearch.jsx`: Autocomplete input querying `playersData.json`. Supports
  debounced filtering, arrow key navigation (Up/Down/Enter/Escape), and outside-click

7.3 Dual-Engine Prediction Architecture (`app/predictor.py`)
To safeguard against runtime failures, serialization mismatches, or missing C-libraries,
`MarketValuePredictor` implements an intelligent dual-engine fallback:

1. Primary Engine (Scikit-Learn Pipeline):
   - Loads `footballiq_best_model.joblib` containing a full scikit-learn `Pipeline`.
   - Feature preprocessor: `ColumnTransformer` with `OneHotEncoder(drop='first')`
     for categorical features ('league', 'position') and `StandardScaler` for
     the 26 numerical and per-90 features.
   - Regressor: Tuned `GradientBoostingRegressor(random_state=42)`.
   - Prediction is executed on a single-row DataFrame, generating `log_pred`.

2. Fallback Engine (Pure NumPy Ridge Regression Solver):
   - Triggered automatically if `joblib.load()` fails or raises an exception.
   - Dynamically ingests `cleaned_player_data.csv` directly from disk.
   - Constructs dummy indicator columns matching training categoricals.
   - Calculates feature means and standard deviations in pure NumPy.
   - Solves the closed-form Ridge Regression normal equation:
     w = (X_bias^T X_bias + λ I)^-1 X_bias^T y
     where λ = 10.0 and y is log_market_value.
   - At inference, vectorizes incoming requests, standardizes using cached means/stds,
     and computes the dot product: log_pred = w · x_bias.
   - Verified Runtime: Executes in < 5ms with zero scikit-learn dependencies.

7.4 Target De-transformation & Clipping
Both engines predict the valuation in natural logarithmic space. The predicted
market value in raw Euros is recovered via the inverse transformation:
raw_pred = max(0.0, exp(log_pred) - 1)  [np.expm1(log_pred)]
Formatted into standard Euro currency strings (e.g. "€77,349,903.66").

8.3 Data Preprocessing & Cleaning Procedures
1. Inner Merge on `player_id`: Matches player metadata in `all_player_profiles.csv`
   with match logs in `all_player_stats.csv`. Players lacking seasonal statistical
   records were dropped.
2. Missing Value Imputation: Position-specific medians were computed for players
   with unrecorded underlying tracking metrics (e.g. xG for lower tier matches).
3. Outlier Clipping: Negative playing minutes or anomalous rating numbers were
   bounded to legitimate domain boundaries (ratings bounded between 1.0 and 10.0).
4. Feature Normalization (Per-90 Calculations):
   n90s = minutes_played / 90.0
   Each volume stat (goals, assists, shots, tackles, etc.) was divided by n90s
   to create rate statistics unaffected by substitute appearances.
5. Log Transformation:
   log_market_value = np.log1p(market_value) = ln(market_value + 1)

9. MACHINE LEARNING PIPELINE & VALUATION ENGINE
================================================================================

9.1 Problem Formulation & Prediction Target
- Target Variable: `market_value` (continuous variable in Euros).
- Transformed Target: `log_market_value` = ln(market_value + 1).
- Rationale: Transfer values span 4 orders of magnitude (€20K to €200M+) exhibiting
  heavy right skewness. Training directly on raw currency induces extreme variance
  and forces models to overfit to rare €100M+ superstars at the expense of regular
  squad players. Log-normalizing stabilizes residual variance across tiers.

9.2 Features Used in ML Model
Categorical Features (2):
- `league` (One-hot encoded, drop='first', handle_unknown='ignore')
- `position` (One-hot encoded, drop='first', handle_unknown='ignore')

Numerical & Per-90 Features (26):
- minutes_played, appearances, matches_started, rating
- goals, assists, expected_goals, expected_assists
- total_shots, shots_on_target, tackles, interceptions, saves
- yellow_cards, red_cards
- goals_per90, assists_per90, xG_per90, xA_per90
- total_shots_per90, shots_on_target_per90, tackles_per90
- interceptions_per90, saves_per90, yellow_cards_per90, red_cards_per90

13. KNOWN ISSUES, TECHNICAL LIMITATIONS & ROADMAP
================================================================================

13.1 Confirmed Technical Issues & Quirks
1. Python 3.14 OpenMP Initialization Delay:
   - Issue: When running under Python 3.14 on Windows, importing scikit-learn
     or unpickling `footballiq_best_model.joblib` incurs a 15–20 second delay
     on the first call due to OpenMP thread pool allocation in `vcomp140.dll`.
   - Workaround: The pure NumPy fallback engine (`_init_numpy_engine`) can be
     forced if instant cold starts are required, or use Python 3.11/3.12 LTS.
2. Vite Large Production Chunk Size Warning:
   - Issue: `npm run build` flags `dist/assets/index-*.js` at 2.99 MB (gzip: 607 KB).
   - Cause: `src/data/playersData.json` (3.36 MB) is bundled directly into the
     main JavaScript chunk.
   - Proposed Fix: Split `playersData.json` into a separate chunk using Rollup
     `manualChunks`, or load it asynchronously on-demand via `fetch('/data/playersData.json')`.
3. Standalone `PlayerPortrait.jsx` is Unmounted:
   - Issue: `src/components/PlayerPortrait.jsx` was built with parallax, halo,
     and dotted grid styling, but is not imported in `Home.jsx` or `Predict.jsx`
     because `Hero.jsx` incorporates its own embedded player layer.
4. Redundant Search Component:
   - Issue: Both `PlayerSearch.jsx` and `SearchBar.jsx` exist in `src/components/`.
     `Hero.jsx` uses `PlayerSearch.jsx`. `SearchBar.jsx` should be consolidated or removed.
5. In-Memory JSON Instead of Database:
   - Issue: All 3,670 player records are loaded into client memory. While fast
     for search, scaling to 50,000 global players will degrade mobile browser performance.

13.2 Future Engineering Roadmap
- Phase 1: Database Migration — Migrate `cleaned_player_data.csv` to PostgreSQL / SQLite
  with pagination endpoints (`GET /api/v1/players?page=1&limit=20`).
- Phase 2: Dynamic Player Cutouts — Integrate real-time player headshot CDN with
  automated portrait cropping and grayscale CSS filter pipelines.
